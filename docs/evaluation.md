## まとめ

固定ブラインドベンチマーク b1（150件、ブラウザの既定の文字列モード）では、次のとおりです。

| 指標 | 値 |
| --- | --- |
| ポジティブ・ネガティブの文で判定できた割合 | **87.0%** |
| 判定できた文での正解率 | **85.7%** |
| Macro-F1 | **82.8%**（形態素解析ありでは 81.4%） |

判定できなかった文は「判定できません」と表示します。中立とは区別します。

---

## 指標

ポジティブ／ネガティブ／中立の **3クラスの分類**として評価します。

* **代表の指標: Macro-F1**（3クラスの F1 の平均。クラスの件数の偏りに左右されにくい）
* Accuracy、クラスごとの Precision / Recall / F1
* 3×3 の混同行列（行: 正解 / 列: 予測）

「判定できません」の文は、Macro-F1 と Accuracy では**中立と予測した**ものとして数えます（以前のバージョンと比べられるように）。

## 3種類のテストセット

| セット | ファイル | 使い方 |
| --- | --- | --- |
| 開発用セット | `data/testset.json` | 誤判定を見て辞書を調整してよい |
| ホールドアウト | `data/holdout.json` | **これを見て辞書を調整しない**。変更の効果の目安。版ごとに入れ替わる |
| ベンチマーク b1 | `data/benchmark/b1.json` | 固定。バージョンの間の比較に使う。個々の文は見ない |

* 開発用セットは辞書に合わせて作られているため、スコアが高く出やすくなります。
* 変更の効果の目安は、**ホールドアウトの Macro-F1** です。
* ホールドアウトは版ごとに入れ替わるため、バージョンの間の比較には**固定ブラインドベンチマーク**を使います。

### ホールドアウトの扱い

1. 辞書を調整している間は `npm run eval -- --only dev` を使い、ホールドアウトの結果を見ないようにします。
2. ホールドアウトは、作業の最後に一度だけ評価します。
3. ホールドアウトの誤判定を直したくなったら、その文を開発用セットへ移し、ホールドアウトには新しい文を補充します。

## 判定できた割合と、判定できた文での正解率

Macro-F1 とは別に、次の3つを報告します（v0.14.0〜）。

* **ポジティブ・ネガティブの文で判定できた割合**（主な指標。v0.15.0〜）: 感情のある文のうち、辞書の語が見つかって判定できた割合。
* **判定できた割合（すべての文）**: 中立の文も含めたすべての文のうち、判定できた割合。
  中立の文は「判定できません」が正しいことも多いため、上限は 100% より低くなります（b1 は3分の1が中立の文なので、最大でも約67%）。
* **判定できた文での正解率**

| セット（v0.15.0） | ポジティブ・ネガティブの文で判定できた割合 | 判定できた割合（すべての文） | 判定できた文での正解率 |
| --- | --- | --- | --- |
| 開発用（727件、形態素解析あり） | 95.8% | 64.5% | 96.6% |
| ホールドアウト v9（60件） | 67.5% | 45.0% | 92.6% |
| **b1（文字列モード＝ブラウザの既定）** | **87.0%**（v0.14.0: 80.0%） | **60.7%**（v0.14.0: 56.0%） | **85.7%**（v0.14.0: 85.7%） |
| b1（形態素解析あり） | 86.0%（v0.14.0: 79.0%） | 60.0%（v0.14.0: 55.3%） | 84.4%（v0.14.0: 85.5%） |

## 形態素解析の効果

**いまの辞書のままでは、形態素解析は精度を上げていません。**
b1 では文字列モードより1〜2文悪く、ホールドアウト v9 では変わりませんでした。

* 形態素解析が良くするのは、**すでに見つかっている語の精度**（否定・語の区切り）です。この精度はもともと高い（ネガティブの Precision 100%）ため、伸びしろが小さくなります。
* 大きく良くするには、見出し語（基本形）で引ける**感情語彙の辞書**が必要です（候補の「日本語評価極性辞書」は、ライセンスを確認できていないため使っていません）。

## 固定ブラインドベンチマーク

`data/benchmark/` にある、辞書を見たことのない作者による**固定の**評価セットです。
ホールドアウトと違って入れ替えず、すべてのバージョンを同じ問題で比べます。

| 版 | 件数 | 作成 | ラベルの確認 |
| --- | --- | --- | --- |
| b1 | 150（ポジティブ・ネガティブ・中立 各50） | リポジトリと辞書にアクセスしない別のエージェント（LLM）が、仕様書だけから作成 | 別の独立したエージェントがテキストだけを見て付け直した。一致 150/150（κ = 1.0） |

### ルール

* **個々の文や誤判定を見ない。** `npm run bench` は集計だけを表示します（`--errors` はありません）。開発者向けの画面の「テスト評価」にも含めません。
* **辞書の調整に使わない。** 調整は開発用セットで行い、ベンチマークは結果の確認だけに使います。
* **編集しない。** `manifest.json` の SHA-256 で固定しています。1文字でも変えると、テストと `npm run bench` が失敗します。変えたいときは新しい版（`b2.json`）を追加します。
* **合否に使わない。** CI ではスコアを報告するだけで、下がっても失敗にしません（合否に使うと、調整の目標になってしまうため）。
* **リリースごとに記録する。** バージョンを上げたら `npm run bench -- --record` で `history.json` に記録します。

### b1 の注意点

* 作成者・確認者はどちらも LLM です。一致率 100% は「このモデルの系統にとってあいまいでない」ことを示すもので、人の手による検証ではありません。
* 長い文（40文字以上）がなく、短い文に偏っています。
* 人が書いた版（b2）を追加すると、より信頼できる比較になります。

辞書を見ていない人が書いたホールドアウトに入れ替えるのが理想です。

## 実行方法

**ブラウザ**: 開発者向けの画面（`#/dev`）の「テスト評価」で、セットを選んで実行します。ユーザー辞書は使いません。

**コマンドライン**: Node.js 22 以上が必要です。最初に一度、依存パッケージ（kuromoji）をインストールします。

```bash
npm ci
```

| コマンド | 内容 |
| --- | --- |
| `npm run eval` | 開発用セットとホールドアウトの指標 |
| `npm run eval -- --only dev` | 開発用セットだけ（辞書の調整中に使う） |
| `npm run eval -- --errors` | 誤判定の一覧も表示 |
| `npm run eval -- --no-morphology` | 文字列モード（ブラウザの既定）で評価 |
| `npm run eval -- --check` | ベースラインより Macro-F1 が下がったら失敗 |
| `npm run eval -- --update-baseline` | ベースラインを更新 |
| `npm run bench` | 固定ブラインドベンチマーク（集計だけ） |
| `npm run bench -- --no-morphology` | 固定ブラインドベンチマークを文字列モードで |
| `npm run bench -- --record` | 現在のバージョンのスコアを記録（形態素解析ありで実行。`--no-morphology` とは併用できない） |
| `npm run gates` | 辞書を変えたときのゲート（[辞書のリファレンス](dictionary.md#語彙の追加手順ゲート)） |
